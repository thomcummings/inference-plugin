# Pricing / packaging / offer architecture

This skill helps a founder or marketing lead make the next pricing, packaging or
offer decision — what to sell, how to package it, what to gate, how to explain the
value, and what to test next — **without fake precision**.

"Offer architecture" is a first-class mode inside it: for services and productised
consulting, the equivalent of a SaaS tier is usually a responsibility contract, not a
feature list.

## Posture

Dry mode by default. This is numbers, money and evidence, so the showmanship dial sits
at zero: precise, sourced, hypotheses and caveats labelled. Recommend principles,
anchors, ranges or tests — not a specific price presented as if analysis discovered it.

If the offer is weak or unclear, do not reject it. Fix the package and the value
narrative first, then the numbers.

## What good looks like — v1 non-negotiables

1. **No fake precision.** Never output a specific price as if analysis found it.
   Recommend principles, anchors, ranges or tests unless there is real benchmark or
   sales evidence.
2. **Package before price.** If the offer is unclear, fix the package and value
   narrative before changing numbers.
3. **Tiers must earn their existence.** Two to four is usually enough. Every tier needs
   a clear buyer state, an upgrade trigger and a responsibility boundary.
4. **Protect margin.** Any offer with expert access, custom work, tool costs or agent
   runs needs caps, fair-use terms, escalation rules or a higher anchor.
5. **Anchor to value and confidence, not cost-plus.** Cost sets the floor for margin;
   the buyer compares against the outcome, avoided risk, headcount, agency, time or
   opportunity cost.
6. **Evidence labels confidence.** Mark validated vs hypothesised; recommend the
   cheapest evidence step when confidence is low.
7. **Avoid tier sprawl and bundle soup.** If buyers need a legend to read the plans,
   the packaging is doing harm.
8. **Do not copy SaaS doctrine into services.** For services / productised consulting,
   a "tier" is usually responsibility transfer, delivery depth, cadence, access and
   scope control.

## When NOT to use

- The real question is product-market fit, retention or growth motion → route to
  `growth-model` first. Pricing can only optimise a model that already has a plausible
  value exchange.
- The ask is a sales deck, objection bank, proposal narrative or proof-gap map → hand
  to `sales-enablement` after this skill clarifies the package and value logic.
- Billing setup, payment tooling, invoice mechanics, tax, discount governance,
  procurement or financial modelling → out of scope.
- The user wants an exact willingness-to-pay number with no evidence → give a
  principled range only if benchmarkable, otherwise recommend evidence-gathering and a
  test.

## Load-bearing questions (ask only if missing)

Ask near the top, then proceed on labelled assumptions. Do not run a long intake form
before giving provisional value.

1. Product/subscription, service/productised consulting, or hybrid?
2. What is the buyer comparing this against — SaaS, agency, hire, consultant, doing
   nothing, internal team time?
3. What outcome is the price meant to capture or de-risk?
4. What evidence exists — paid customers, sales calls, usage, renewal/churn, or just a
   hypothesis?
5. What must not be included because it would destroy margin or create delivery drag?
6. Optimising for conversion, expansion, margin, repositioning or simplicity?

## Workflow — diagnose in this order (the sequence is the value)

### 1. Commercial object

Identify what is being sold — the pricing risk differs by object. Full table in
`references/value-metrics-and-tiering.md`.

| Object | Main pricing risk |
|---|---|
| Product subscription (SaaS, AI tool, membership) | weak value metric, confusing tiers, bad upgrade path |
| Usage/volume (API, credits, seats+usage, data) | value-metric misfit, bill shock, margin leakage |
| Productised service (audit, sprint, kit, managed advisor) | hours disguised as value, scope creep, weak responsibility boundary |
| Advisory/retainer (fractional CMO, expert access) | vague value, unlimited access, margin erosion |
| Premium implementation (agent team, bespoke workflow) | under-anchoring against SaaS instead of headcount/agency |
| Hybrid (software + expert + implementation) | collapsed tiers, unclear who owns the outcome |

### 2. Value anchor

Force one sentence:

> The buyer is not buying `<feature/service>`; they are buying `<business outcome or
> risk reduction>`.

Candidates: revenue/conversion, speed to decision, avoided bad hire/agency/build,
confidence in a high-stakes call, access to scarce expertise, workflow capacity or
role replacement, reduced risk/governance, proprietary data/context/judgement.

### 3. Buyer confidence and proof

Before touching price or tiers, ask whether the buyer believes the promise. Climb the
highest-quality evidence available and mark the rest:

1. Direct willingness-to-pay / closed deals
2. Comparable customer purchases / renewal behaviour
3. Usage, expansion or retention signal
4. Sales objections and lost-deal reasons
5. Pricing-page analytics / conversion data
6. Founder judgement and market analogy

Thin evidence caps confidence, not usefulness: produce the best provisional package and
the cheapest proof step.

### 4. Packaging clarity

Can a buyer answer: which package is for me; why it beats the cheaper one; what changes
when I grow; what's included/excluded; who does the work (customer, software, expert,
team, hybrid); what risk paying more removes; what the next upgrade trigger is? If not,
it's an offer-architecture problem, not yet a pricing one.

### 5. Value metric / unit of growth

For product and usage models, diagnose what scales with value (seats, active
accounts/projects, volume, revenue managed, workspaces/brands, outcomes, managed
capacity). Good metrics map to value received, buyer budget logic and cost-to-serve;
bad ones punish adoption, surprise the buyer, or fail to expand. Detail and fit tests
in `references/value-metrics-and-tiering.md`. For services, translate the value metric
into the responsibility/capacity unit — see
`references/services-offer-architecture.md`.

### 6. Tier logic and responsibility contract

Tiers should represent a different **responsibility contract**, not a longer feature
list. The strongest model:

| Tier type | Customer contract | What changes |
|---|---|---|
| Self-serve / Core / BYOK | Customer operates | frameworks, cockpit, templates, BYOK compute, limited support |
| Advisor / managed | Shared responsibility | managed advisor, cadence, context, bounded escalation, fair-use usage |
| Agent Team / premium | Provider takes more responsibility | specialist network, custom workflows, richer integrations, higher-touch delivery |

Generalises as DIY → guided → done-with-you → done-for-you; tool → workflow → managed
outcome; template → diagnostic → sprint → retained operating layer.

### 7. Margin and delivery constraints

State the margin risks on every recommendation: unbounded human access; custom
implementation sneaking into a fixed package; uncapped inference/tool cost; too many
bespoke deliverables; the cheapest tier cannibalising the premium; support scaling
faster than revenue; hidden onboarding effort. Protect advisory margin — diagnose,
design, decide, direct; don't produce/manage/operate/maintain unless the offer is
explicitly priced as implementation.

### 8. Experiment path

End with a decision or a test, never a spreadsheet. Test menu in
`references/pricing-experiments.md` — price-framing on sales calls, package-wording
tests, fake-door upgrade/add-on, segmented proposal A/B (with ethics guardrails),
concierge/pilot of the premium tier, annual-prepay test, pricing-page clarity test,
plan-distribution review, lost-deal value interviews.

## Output modes

Pick the mode that fits; scaffolds in `references/` where noted, otherwise inline.

- **A. Pricing-page teardown** — user gives a live page or current packages. Output:
  the call (keep/change/rethink); buyer-read diagnosis; package clarity table; pricing-
  relevant value & proof gaps; margin/cannibalisation risks; changes in priority order;
  a one or two test plan with signal and threshold.
- **B. Package architecture** — a new offer/product needs structuring. Output:
  recommended package shape; package table (buyer state, promise, included, excluded,
  delivery responsibility, upgrade trigger, margin guardrail); 3-5 sentence offer
  narrative; commercial constraints; what to test before locking.
- **C. Tier recommendation** — user has candidate tiers. Output: run-this-shape call;
  cut/merge/rename; tier responsibility map; upgrade path; risk watch (cannibalisation,
  tier cliff, hidden support load, unclear premium value).
- **D. Value-metric diagnosis** — SaaS/AI/usage/data/membership. Output: current metric
  read; ranked candidate metrics with pros/cons; fit tests; keep/add-secondary/change-
  later/instrument-first recommendation; validation path.
- **E. Offer narrative** — the package exists but is hard to explain. Output: core value
  line; responsibility line; why this package exists; why upgrade; what not to say.
- **F. Pricing experiment plan** — decision uncertain, needs evidence. Output: decision
  to de-risk; assumption tested; lowest-risk test design; audience/segment; signal and
  threshold; failure modes / ethics guardrails; the decision made after the test.

Save as a draft/working artefact; hand a polished client-facing version to `doc-system`.

## IMSM component mapping

Mostly Expert Judgment + Commercial Constraints, using Memory and Evaluation to avoid
repeating old mistakes.

| Component | Use |
|---|---|
| Objective | What the decision should serve: conversion, expansion, retention, margin, positioning, buyer confidence. |
| Training Data | Sales calls, usage, closed/lost, renewal/churn, customer quotes, proposal history, competitor pages, analytics. |
| Memory | Prior pricing decisions, repeated objections, package changes tested, segment WTP learnings, margin lessons. |
| Infrastructure | Pricing page, checkout/billing, CRM fields, proposal templates, analytics, product gates. |
| Expert Judgment | The actual call: what to package, simplify, cap, test, and not believe yet. |
| Orchestration | Hand-offs to sales-enablement, growth-bets, product, finance, web/copy, and human approval before public changes. |
| Evaluation | Conversion, plan mix, expansion, churn, sales-cycle friction, objection frequency, margin, usage/cost leakage, test thresholds. |
